## 1. これは何か

社内の業務システムを1つの入口に束ねたプラットフォーム。利用者はポータル画面にログインし、そこから自分が使えるシステムへ移動する。

第1弾として **備品在庫管理システム** を実装し、以降システムを追加していく。

```
                    ┌─────────────────┐
   ログイン  ───▶   │  ポータル画面    │
                    │  （使えるシステム │
                    │    が並ぶ）      │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
      ┌──────────────┐ ┌──────────┐ ┌──────────┐
      │ 備品在庫管理  │ │ （今後）  │ │ （今後）  │
      │  /inventory  │ │          │ │          │
      └──────────────┘ └──────────┘ └──────────┘
```

## 2. 構成の方針

### 2.1 単一アプリケーション内でモジュールを分割する

**採用：** Laravel・React ともに1つのアプリケーションとし、システムごとの機能は名前空間とルートで分離する。

**採用しなかった案：** システムごとに独立したアプリケーションを立て、ポータルが入口となる構成。

| 観点 | 単一アプリ（採用） | システムごとに独立 |
|---|---|---|
| 認証 | セッションを共有するだけで済む | SSO（OIDC 等）の実装が必要 |
| ユーザー・部署マスタ | 1か所で管理 | どこかを正としてシステム間で同期が必要 |
| デプロイ | 1回 | システム数だけ必要 |
| システム間の独立性 | 低い（同じDBを共有） | 高い |
| 実装コスト | 低い | 高い |

**判断根拠：** 社内向けで利用者が同一組織に閉じており、システム間でユーザー・部署が完全に共通する。この条件下では、独立アプリ構成が得られる「システム間の独立性」に見合う利点がない。一方でコストは SSO とデータ同期という形で確実に発生する。

将来的にどれか1つのシステムだけ切り出す必要が生じた場合に備え、**モジュール境界を意識した配置**（§3）にしておく。

### 2.2 モジュール分割の原則

| 原則 | 内容 |
|---|---|
| 共通基盤は薄く保つ | 認証・ユーザー・部署・システム利用権限のみ。特定システムの都合を持ち込まない |
| システム間で直接参照しない | 備品在庫管理のコードが他システムのモデルを直接使うことは禁止。必要なら共通基盤に引き上げる |
| DB のテーブルもモジュールに属する | `items` は在庫モジュールのもの。他システムから直接 JOIN しない |

## 3. ディレクトリ構成

### 3.1 バックエンド（Laravel）

```
backend/app/
├── Models/
│   ├── User.php                 共通
│   ├── Department.php           共通
│   ├── System.php               共通
│   ├── SystemUserRole.php       共通
│   └── Inventory/               在庫モジュール
│       ├── Item.php
│       ├── ItemStock.php
│       └── ...
├── Http/
│   ├── Controllers/
│   │   ├── Auth/                認証
│   │   ├── Portal/              ポータル
│   │   └── Inventory/           在庫モジュール
│   └── Requests/
│       ├── Auth/
│       └── Inventory/
├── Services/
│   └── Inventory/               在庫の業務ロジック
│       └── StockService.php
└── Policies/
    ├── UserPolicy.php
    └── Inventory/
```

ルートは `routes/api.php` の中でプレフィックスとグループで分ける。

```
/api/v1/auth/*         認証
/api/v1/portal/*       ポータル
/api/v1/users/*        ユーザー管理（共通）
/api/v1/inventory/*    備品在庫管理
```

> **在庫の API パスが `/api/v1/inventory/items` になる点に注意。** 単体システムとして設計していた頃の `/api/v1/items` から変わる。

### 3.2 フロントエンド（React）

```
frontend/src/
├── features/
│   ├── auth/          ログイン
│   ├── portal/        ポータル画面
│   └── inventory/     備品在庫管理
│       ├── api/
│       ├── components/
│       ├── hooks/
│       └── pages/
├── shared/            全機能で使う UI・ユーティリティ

│   └── hooks/

```

```
/login          ログイン

/inventory/*    備品在庫管理
```

## 4. 権限の考え方

**ロールはシステムごとに持つ。**

```
users
  └─ system_user_roles ─┬─ (system: inventory,  role: admin)
                        └─ (system: attendance, role: member)
```

同じ人が、あるシステムでは管理者、別のシステムでは一般利用者、という状態を表現できる。

| 権限の種類 | 保持場所 | 例 |
|---|---|---|
| 全体管理者 | `users.is_system_admin` | ユーザー登録、部署マスタ、システムの有効/無効 |
| システム別ロール | `system_user_roles.role` | 在庫システムの `admin` / `staff` / `member` |

**ポータルに表示されるのは、そのユーザーが `system_user_roles` に行を持つシステムだけ**とする。行が無ければアクセス権が無いということであり、ポータルにも並ばない。

ロール名はシステムごとに異なりうるため、`role` は ENUM ではなく VARCHAR とし、**どの値が有効かは各システムが定義する**（共通DB設計書 §2.4）。

## 5. 認証

| 項目 | 内容 |
|---|---|
| 方式 | Laravel Sanctum の SPA 認証（Cookie ベース） |
| 適用範囲 | **全システム共通。**一度ログインすればポータルからどのシステムへも移動できる |
| 認可 | システムへの入口で `system_user_roles` を確認し、権限が無ければ 403 |

システムごとに再ログインを求めることはしない。単一アプリケーション内でセッションを共有するため、追加の仕組みは不要。
