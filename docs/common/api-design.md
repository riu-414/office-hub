# 共通 API 設計書

| 項目 | 内容 |
|---|---|
| バージョン | 1.0 |
| 作成日 | 2026-09-06 |
| 関連文書 | `docs/architecture.md` / `docs/common/requirements.md` / `docs/common/database-design.md` |

**本書 §1 の共通仕様は全システムの API に適用される。** 各システムの API 設計書はこれを前提とし、重複して書かない。

---

## 1. 共通仕様

### 1.1 基本方針

| 項目 | 内容 |
|---|---|
| スタイル | REST |
| ベース URL | `/api/v1` |
| データ形式 | JSON |
| 日時形式 | ISO 8601（例：`2026-09-06T14:30:00+09:00`） |
| 日付形式 | `YYYY-MM-DD` |
| 命名 | リクエスト・レスポンスともにスネークケース |

**パスの構成**

```
/api/v1/auth/*         認証
/api/v1/portal/*       ポータル
/api/v1/users/*        ユーザー管理
/api/v1/departments/*  部署マスタ
/api/v1/systems/*      システムマスタ
/api/v1/<システムキー>/*  各システム（例：/api/v1/inventory/items）
```

**各システムの API は必ずシステムキーをプレフィックスに持つ。** これによりルーティングの段階でモジュールが分離され、権限チェックもミドルウェアで一括して掛けられる。

### 1.2 認証

**Laravel Sanctum の SPA 認証（Cookie ベース）**を全システム共通で使う。

```
1. GET  /sanctum/csrf-cookie      → XSRF-TOKEN Cookie を取得
2. POST /api/v1/auth/login        → セッション Cookie が発行される
3. 以降のリクエストは Cookie を自動送信し、X-XSRF-TOKEN ヘッダを付与する
```

| 項目 | 内容 |
|---|---|
| セッション Cookie | `HttpOnly`, `Secure`, `SameSite=Lax` |
| CSRF | 状態変更系に `X-XSRF-TOKEN` ヘッダを必須とする |
| セッション有効期限 | 8 時間。操作があれば延長 |

**一度ログインすればすべてのシステムを利用できる。** システムごとの再認証は求めない。

> **トークン方式（Bearer + localStorage）を選ばなかった理由：** アクセストークンを localStorage に置くと XSS でトークンごと盗まれる。`HttpOnly` Cookie なら JavaScript から読めない。

### 1.3 認可

2段階で判定する。

```
① ミドルウェア：/api/v1/<システムキー>/* へのアクセス時に
   system_user_roles に該当行があるか確認 → 無ければ 403 SYSTEM_ACCESS_DENIED

② Policy：各エンドポイントで、そのシステムにおけるロールを確認
   → 権限不足なら 403 FORBIDDEN
```

**①をミドルウェアに置くことで、各システムの実装が権限チェックを書き忘れても、システム自体には入れない。** 個別の実装ミスが「他システムのデータが見える」事故に直結しないようにする。

### 1.4 レスポンス形式

**単一リソース**

```json
{ "data": { "id": 12, "name": "..." } }
```

**一覧（ページネーション）**

```json
{
  "data": [ /* ... */ ],
  "meta": { "current_page": 1, "per_page": 20, "total": 137, "last_page": 7 }
}
```

すべてのレスポンスは API Resource で整形し、Eloquent モデルをそのまま返さない。

### 1.5 エラー形式

```json
{
  "message": "在庫が不足しています。",
  "error_code": "INSUFFICIENT_STOCK",
  "errors": { "quantity": ["出庫数が手元在庫（8本）を超えています。"] }
}
```

| フィールド | 説明 |
|---|---|
| `message` | 画面にそのまま表示できる日本語のメッセージ |
| `error_code` | フロントが分岐に使う機械可読なコード |
| `errors` | 項目別エラー。フォームの各入力欄に紐付ける |

### 1.6 HTTP ステータスコードの方針

| コード | 用途 |
|---|---|
| 200 | 取得・更新の成功 |
| 201 | 作成の成功 |
| 204 | 削除の成功（本文なし） |
| 401 | 未認証 |
| 403 | 権限不足 |
| 404 | リソースが存在しない |
| 409 | **競合**（楽観ロックの衝突、二重確定） |
| 422 | バリデーションエラー、業務ルール違反 |
| 429 | レート制限 |
| 500 | サーバエラー |

### 1.7 共通エラーコード

| `error_code` | HTTP | 意味 |
|---|---|---|
| `UNAUTHENTICATED` | 401 | 未ログイン、またはセッション切れ |
| `SYSTEM_ACCESS_DENIED` | 403 | そのシステムの利用権限が無い |
| `FORBIDDEN` | 403 | システム内での権限不足 |
| `VALIDATION_FAILED` | 422 | 入力値エラー |
| `STALE_VERSION` | 409 | 楽観ロックの衝突 |
| `REQUEST_IN_PROGRESS` | 409 | 同じ冪等性キーの処理が進行中 |
| `IDEMPOTENCY_KEY_REUSED` | 422 | 同じ冪等性キーで異なる内容を送信した |

各システム固有のエラーコードは、そのシステムの API 設計書に定義する。

### 1.8 冪等性

**状態を変える POST のうち、二重実行が業務上の被害になるもの**は、リクエストヘッダ `Idempotency-Key`（UUID）を必須とする。

```
Idempotency-Key: 6f8a1c2e-3b4d-4e5f-8a9b-0c1d2e3f4a5b
```

- 同じキーで再送された場合、処理は行わず**初回と同じレスポンスを返す**
- キーと結果は `idempotency_keys` テーブルに 24 時間保持する（共通 DB 設計書 §2.6）
- 重複の検出は **PRIMARY KEY への INSERT が失敗するかどうか**で行う
- フロントは送信ボタン押下時に UUID を生成し、リトライ時も同じキーを使う

**どのエンドポイントに適用するかは各システムが決める。** 在庫の増減のように、二重に実行されると数値がずれるものが対象。

> **導入する理由：** 通信の再送やダブルクリックによる二重登録は、業務システムで最も起きやすく影響が大きい。ボタンの二度押し防止（フロント）だけでは、通信タイムアウト後のリトライを防げない。

### 1.9 一覧 API の共通パラメータ

| パラメータ | 例 | 説明 |
|---|---|---|
| `page` | `2` | ページ番号（既定 1） |
| `per_page` | `50` | 件数（既定 20、最大 100） |
| `sort` | `-updated_at` | 並べ替え。先頭の `-` で降順 |
| `q` | `ボールペン` | キーワード検索 |

### 1.10 レート制限

| 対象 | 制限 |
|---|---|
| ログイン | 同一 IP から 5 回 / 分 |
| その他の API | 認証ユーザーあたり 120 回 / 分 |

## 2. エンドポイント一覧

### 2.1 認証

| メソッド | パス | 権限 | 説明 |
|---|---|---|---|
| GET | `/sanctum/csrf-cookie` | 誰でも | CSRF トークン取得 |
| POST | `/api/v1/auth/login` | 誰でも | ログイン |
| POST | `/api/v1/auth/logout` | 認証済 | ログアウト |
| GET | `/api/v1/auth/me` | 認証済 | ログイン中ユーザーの情報 |
| PUT | `/api/v1/auth/password` | 認証済 | パスワード変更 |
| PUT | `/api/v1/auth/profile` | 認証済 | 氏名の変更 |

### 2.2 ポータル

| メソッド | パス | 権限 | 説明 |
|---|---|---|---|
| GET | `/api/v1/portal/systems` | 認証済 | **利用可能なシステム一覧** |

### 2.3 ユーザー・マスタ管理

| メソッド | パス | 権限 | 説明 |
|---|---|---|---|
| GET | `/api/v1/users` | 全体管理者 | 一覧・検索 |
| POST | `/api/v1/users` | 全体管理者 | 登録 |
| GET | `/api/v1/users/{user}` | 全体管理者 | 詳細（システム利用権限を含む） |
| PUT | `/api/v1/users/{user}` | 全体管理者 | 更新 |
| DELETE | `/api/v1/users/{user}` | 全体管理者 | 無効化（論理削除） |
| PUT | `/api/v1/users/{user}/system-roles` | 全体管理者 | **システム利用権限の一括設定** |
| GET/POST/PUT/DELETE | `/api/v1/departments` | 参照:認証済 / 更新:全体管理者 | 部署マスタ |
| GET/PUT | `/api/v1/systems` | 全体管理者 | システムマスタ |

## 3. 主要エンドポイント詳細

### 3.1 `POST /api/v1/auth/login`

**リクエスト**

```json
{ "email": "admin@example.com", "password": "password" }
```

| 検証 | 内容 |
|---|---|
| メール | 小文字に正規化してから照合する |
| 無効化 | `is_active` が false のユーザーは 422。**「アカウントが無効です」ではなく「メールアドレスまたはパスワードが正しくありません」と返す**（アカウントの存在を推測させないため） |

**レスポンス 200** — `/auth/me` と同じ内容を返し、フロントが再取得しなくて済むようにする。

---

### 3.2 `GET /api/v1/auth/me`

```json
{
  "data": {
    "id": 5,
    "name": "田中 太郎",
    "email": "tanaka@example.com",
    "department": { "id": 1, "name": "総務部" },
    "is_system_admin": false,
    "systems": [
      { "key": "inventory", "name": "備品在庫管理", "role": "admin" }
    ]
  }
}
```

> **`systems` を含める理由：** フロントはこの配列だけで「ポータルに何を出すか」「在庫システム内でどのメニューを出すか」を判断できる。画面ごとに権限を問い合わせる往復が不要になる。
>
> ただし**表示制御はあくまで UX のためであり、認可の本体はサーバ側**にある（§1.3）。

---

### 3.3 `GET /api/v1/portal/systems`

ポータル画面に並べるシステムの一覧。

**レスポンス 200**

```json
{
  "data": [
    {
      "key": "inventory",
      "name": "備品在庫管理",
      "description": "社内備品の在庫・貸出・棚卸しを管理します",
      "icon": "package",
      "role": "admin",
      "path": "/inventory",
      "notification_count": 6
    }
  ]
}
```

| 項目 | 説明 |
|---|---|
| `role` | そのユーザーのこのシステムでのロール |
| `notification_count` | そのユーザー向けの要対応件数（在庫僅少＋返却期限超過など） |

**返す条件**

```
systems.is_active = true
  AND system_user_roles に (該当ユーザー, そのシステム) の行が存在する
```

行が無いシステムは**一切返さない**。存在すら知らせない。

> **`notification_count` の取り方：** ポータルが各システムのテーブルを直接数えると、モジュール境界が壊れる（`docs/architecture.md` §2.2）。各システムが「自分の通知件数を返す」インターフェースを実装し、ポータルはそれを呼ぶだけにする。
>
> 件数の集計はシステムごとにコストが異なるため、**この項目は Should**（共通要件定義書 C-204）。まずは件数なしで実装し、後から足す。

---

### 3.4 `PUT /api/v1/users/{user}/system-roles`

ユーザーのシステム利用権限をまとめて設定する。

**リクエスト**

```json
{
  "system_roles": [
    { "system_key": "inventory", "role": "staff" }
  ]
}
```

**処理**

送られた配列を**あるべき状態そのもの**として扱う。配列に無いシステムの権限は削除される。

| 検証 | 内容 |
|---|---|
| `system_key` | `systems` に存在し、有効であること |
| `role` | **そのシステムが定義するロールの集合に含まれること**（在庫なら `admin`/`staff`/`member`） |
| 重複 | 同じ `system_key` が2つ以上あれば 422 |

> **差分（追加/削除）ではなく全体を送らせる理由：** 権限画面はチェックボックスの一覧であり、利用者は「最終的にこうしたい」を操作している。差分方式にすると画面の状態と送信内容の変換が必要になり、取りこぼしが起きやすい。
>
> ロールの有効値の検証は共通基盤が各システムに問い合わせる形にし、**共通基盤が個別システムのロール名を直接知らないようにする**。
