## 1. 目的と範囲

全システムで共通して使う基盤の要件を定める。

| 含む | 含まない |
|---|---|
| ポータル画面 | 各システムの業務機能 |
| 認証（ログイン・ログアウト） | 各システム内の権限判定ロジック |
| ユーザー管理 | |
| 部署マスタ | |
| システムマスタと利用権限 | |

各システム固有の要件は `docs/<システム名>/requirements.md` に書く。

---

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| システム | ポータルから遷移できる業務アプリケーション単位。例：備品在庫管理 |
| システムキー | システムを識別する英字の短い名前。URL に使う。例：`inventory` |
| 全体管理者 | ユーザー・部署・システムマスタを管理できる人。`users.is_system_admin` が真 |
| システムロール | あるシステムの中での役割。システムごとに定義が異なる |

---

## 3. ロールと権限

### 3.1 二層構造

権限を2つの層に分ける。

| 層 | 保持場所 | 意味 |
|---|---|---|
| **全体管理者** | `users.is_system_admin` | 基盤そのものを管理できるか |
| **システムロール** | `system_user_roles.role` | 各システム内での役割 |

**同じ人が、システムごとに異なる役割を持てる**ことが要件である。

> 総務の田中さんは備品在庫管理では管理者だが、将来追加される勤怠管理では一般利用者、という状態を表現できる必要がある。

### 3.2 全体管理者にできること

- ユーザーの登録・編集・無効化
- ユーザーへのシステム利用権限の付与・剥奪
- 部署マスタの管理
- システムマスタの管理（表示名、並び順、有効/無効）

**全体管理者であることは、各システムの管理者であることを意味しない。** 備品在庫管理を操作するには、その人にも `system_user_roles` の行が必要である。基盤の管理者が業務データを自由に触れてしまうと、監査上の責任範囲が曖昧になるため。

### 3.3 システムロール

ロール名の集合は**システムごとに定義する**。備品在庫管理は `admin` / `staff` / `member` の3種（`docs/inventory/requirements.md` §4）。

将来のシステムが別のロール体系を持つことを許容するため、DB では ENUM ではなく文字列として保持し、有効な値の検証は各システムの実装が担う。

## 4. 機能要件

優先度は MoSCoW 法。

### 4.1 認証

| ID | 機能 | 優先度 | 概要 |
|---|---|---|---|
| C-101 | ログイン | Must | メールアドレス＋パスワード。**無効化されたユーザーはログインできない** |
| C-102 | ログアウト | Must | セッションを破棄 |
| C-103 | ログイン中ユーザーの取得 | Must | 氏名・部署・全体管理者フラグ・利用可能システム一覧 |
| C-104 | パスワード変更 | Must | 本人のみ。現在のパスワードを要求する |
| C-105 | パスワードリセット（メール） | Should | |
| C-106 | ログイン失敗の回数制限 | Must | 同一 IP から 5 回/分 |

### 4.2 ポータル

| ID | 機能 | 優先度 | 概要 |
|---|---|---|---|
| C-201 | システム一覧の表示 | Must | **ログイン中ユーザーが利用権限を持つシステムのみ**をカード形式で表示 |
| C-202 | システムへの遷移 | Must | カードをクリックして各システムのトップへ |
| C-203 | 利用可能なシステムが無い場合の表示 | Must | 「利用できるシステムがありません。管理者にお問い合わせください」 |
| C-204 | 各システムの通知件数の表示 | Should | カード上にバッジ表示（例：在庫僅少 6 件）。**システム側が件数を返す共通の仕組みを設ける** |
| C-205 | ヘッダから他システムへの切替 | Should | 各システムの画面からポータルに戻らず移動できる |

> C-204 は「ポータルが各システムの中身を知っている」状態になりやすい。ポータルは件数の取得方法を知らず、**各システムが自分の通知件数を申告する**形にして、モジュール境界を守る（`docs/architecture.md` §2.2）。

### 4.3 ユーザー管理

| ID | 機能 | 優先度 | 概要 |
|---|---|---|---|
| C-301 | ユーザー一覧・検索 | Must | 氏名・メール・部署・状態で絞込 |
| C-302 | ユーザー登録 | Must | 全体管理者のみ。初期パスワードを発行 |
| C-303 | ユーザー編集 | Must | 氏名、メール、部署、全体管理者フラグ |
| C-304 | ユーザー無効化 | Must | 論理削除。**在庫履歴などの過去データは残す** |
| C-305 | システム利用権限の付与・剥奪 | Must | ユーザーごとに、どのシステムでどのロールかを設定 |
| C-306 | 自分のプロフィール編集 | Should | 氏名の変更 |

### 4.4 部署マスタ

| ID | 機能 | 優先度 | 概要 |
|---|---|---|---|
| C-401 | 部署の登録・編集・削除 | Must | 全体管理者のみ。階層は持たない |

### 4.5 システムマスタ

| ID | 機能 | 優先度 | 概要 |
|---|---|---|---|
| C-501 | システムの一覧・編集 | Should | 表示名、説明、並び順、有効/無効 |
| C-502 | システムの無効化 | Should | 一時的にポータルから隠す。権限データは保持したまま |

システムの追加そのものは実装を伴うため、レコードはシーダで投入する。画面から新規作成はできない。

## 6. 非機能要件

全システムに共通して適用する。

| 区分 | 要件 |
|---|---|
| 対応ブラウザ | Chrome / Edge / Safari の最新 2 バージョン |
| 画面サイズ | PC（1280px 以上）を主とし、タブレット（768px 以上）でも操作可能 |
| 認証 | Laravel Sanctum の SPA 認証。セッション有効期限 8 時間 |
| セキュリティ | CSRF / XSS / SQL インジェクション対策。パスワードは bcrypt |
| 権限判定 | **必ずサーバ側で行う。**フロントの表示制御は補助 |
| 言語・地域 | 日本語のみ。タイムゾーンは Asia/Tokyo |
| バックアップ | DB を日次フルバックアップ、7 世代保持 |

## 7. 決定事項

| # | 論点 | 決定 | 判断根拠 |
|---|---|---|---|
| 1 | ロールを全システム共通で1つにするか | **システムごとに持つ**（`system_user_roles`） | 1つの `users.role` では「在庫では管理者、勤怠では一般」を表現できない。ポータルの存在意義がシステム別の権限管理にあるため、ここを妥協すると構成の意味が失われる |
| 2 | 全体管理者に全システムの操作権限を与えるか | **与えない** | 基盤の管理者が業務データを操作できると、監査上の責任範囲が曖昧になる。必要なら自分に権限を付与すればよく、その行為自体が記録に残る |
| 3 | ポータルに表示するシステムの決め方 | **`system_user_roles` に行があるものだけ** | 権限とポータル表示を別管理にすると必ず食い違う。単一の情報源にする |
| 4 | ロールの型 | **VARCHAR**（ENUM にしない） | システムごとにロール体系が異なりうる。ENUM だとシステム追加のたびに `users` 系テーブルの ALTER が必要になる |
| 5 | システムの追加方法 | **シーダで投入。画面からは作れない** | システム追加は実装を伴う。DB にレコードだけ増やしても画面は存在しない |
